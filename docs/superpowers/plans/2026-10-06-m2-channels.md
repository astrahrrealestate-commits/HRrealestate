# M2 Channels Implementation Plan

> **For agentic workers:** execute task-by-task with `/ship` (RED → GREEN → REFACTOR → G1 → G2 → review → commit).
> Execution mode chosen by user: **native, via /ship**. Each task lists the tests to write first; test code is
> written in the RED step against the interfaces below (this plan carries interfaces + test cases, not test bodies).

**Goal:** WhatsApp and Gmail ingestion (plus outbound adapters) running end to end with fake providers, switchable to
real providers by credentials + config, proven by `make sim-demo` (G5) and `make live-check` (go-live gate).

**Architecture:** Ports (Protocols) per provider capability in `app/channels/<channel>/ports.py`; fakes and real
adapters behind a settings-driven registry. Shared ingestion path: verify → raw_event + DBOS enqueue in one transaction
→ `process_event` workflow → `Message` → storage + rows → route. See spec.

**Tech Stack:** FastAPI, DBOS, SQLAlchemy/Alembic, Pydantic v2, httpx (WhatsApp Cloud API / 360dialog transport),
google-api-python-client + google-auth (Gmail, Pub/Sub OIDC), mail-parser-reply, inscriptis, boto3; tests: respx,
moto, cryptography (test JWT signing), syrupy, testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-06-estateos-m2-channels-design.md`

## Global Constraints

- All M1 constraints and CLAUDE.md invariants hold (company scoping, Postgres-before-work, send isolation, no Redis).
- No test may need real provider credentials except those marked `live` (deselected by default).
- `env == "prod"` with any fake provider or local storage → API and worker refuse to start.
- Outbound adapters are importable only by `app.sender` (import-linter contract extended).
- `app.dev` (simulator) is imported by nothing else in `app`.
- Fixtures follow documented provider shapes and are PII-redacted (`/record-fixture`).
- Deviation from spec §1: **pywa dropped** — it hard-codes `graph.facebook.com` (pywa/api.py:41), incompatible with the
  360dialog route. Inbound uses our Pydantic models of the documented webhook schema; outbound uses typed Cloud API
  JSON builders + one httpx transport configured per provider (base URL, auth header, path). ADR 0003 amended.

## Review Focus

1. **Duplicate and reordered delivery**: the same WA webhook delivered twice, a webhook carrying 3 messages + 2
   statuses, a status arriving before its message, a Gmail push for an already-synced historyId, two pushes racing →
   exactly one raw_event / message per provider id, no lost messages. Tasks 7–9.
2. **Forged or broken requests**: wrong/missing `X-Hub-Signature-256`, body tampered after signing, wrong verify token,
   Pub/Sub JWT with wrong audience/issuer/expired/unsigned → 401/403, nothing written. Tasks 3, 6, 8.
3. **Ugly email**: HTML-only, nested multipart/alternative inside multipart/mixed, latin-1/quoted-printable, German
   quote headers ("Am 05.10.2026 um 09:12 schrieb …"), Outlook "Von:/Gesendet:" blocks, inline images, empty body with
   attachment only → readable `text`, attachments stored, never a crash. Task 5.
4. **Expired Gmail history id** (404 from history.list) and a missed push → full resync / hourly backfill recovers
   without duplicates. Tasks 6, 9.
5. **Unknown provider event types** (reactions, location, unsupported, system messages, template status) → stored as
   raw_event with a safe `Message` (text placeholder, metadata.type) or ignored explicitly — never a 500 to the
   provider (providers retry on non-2xx and would flood us). Tasks 3, 8.
